# Codex — six-stage Astro site conversion rules

This repository is the **approved visual and functional template**. Preserve it when creating another branded, game-specific website. The MW4 text, sample images, claims and referral URLs are starter content to replace, not evidence for the new game. Work only in the open site clone. The owner uses six external prompts supplied separately, in this order: **1 conversion, 2 forum import, 3 media, 4 internal links, 5 final audit, 6 GitHub push**. No reviews stage. Do not revive content packs, approval installers, hidden draft modes, or staged-source workflows.

## Preserve the template by default
- Keep the existing Astro pages/components, purple styling, typography, spacing, bento/grids, mobile/tablet/desktop breakpoints, galleries, animations, accessibility, icon-label alignment, support UI, and the **existing localized CTA text**. No redesign or cross-site cosmetic refactoring. `docs/VISUAL_FIDELITY.md` defines the visual contract.
- **Comparison lock:** `src/components/WhySetupSection.astro` retains feature rows plus the two columns (this site's product / **Other providers**), green checks, X/cross icons, and localized **Varies** tooltip/screen-reader wording. Never swap it for prose/cards or claim that every competitor lacks a feature. Adjust descriptions for the new product without invented competitor claims.
- **Checkout lock:** no on-site prices, duration selectors, totals, scarcity/“Limited” badges, or pricing tables. Keep checkout card layout, mobile bar, and exact localized **“View Purchase Options”** product CTA labels; no text/style changes. Navbar primary CTA and hero “View products” CTA go **directly to `CHECKOUT_URLS.primary`**, while product-page buttons keep their existing `/go/` routes. Configure four product referrals only in `src/config/checkout-redirects.mjs` and preserve the three `/go/` support destinations from `src/config/outbound-redirects.mjs`.
- No review pages, fake reviews, ratings, review schema, or review-import workflow. No support-email input or new support workflow. Keep shipped logo/favicon and protected HWID Spoofer/Skin Changer/Cloud DMA media.

## Content, research, quality and SEO
- Use the owner's **main product summary** as the primary product-fact input. Do focused verification only for important unknown or conflicting claims, not repeated broad research. Never invent features, requirements, patch status, rankings, testing, usage statistics, user experiences or guarantees.
- **Persuasive, natural commercial writing**: specific audience benefits, clear headings, compelling opening, scannable paragraphs and realistic feature explanations. Keep hero/card slots concise; fill product introductions, feature breakdowns, utilities, setup, FAQ and guides with detailed information **as much as the existing layout supports**. Avoid thin one-line descriptions, boilerplate, generic SEO padding and game-name swaps. Rewrite supporting utility body copy freshly for each site while preserving their accurate features/headings and media.
- Treat the site's own brand as the storefront voice. Do not gratuitously insert supplier/commission terminology or bogus “independently tested” labels into marketing copy. Accurately describe external checkout/support and do not misrepresent ownership, fulfillment, sponsorship or any legally required transparency. Do not fabricate testimonials or forum experiences.
- Complete useful English text and one keyword/URL-intent map **once**, then adapt naturally for ES/DE/FR using existing locale architecture. Preserve canonical URLs, hreflang, page metadata, robots/sitemap, appropriate structured data and internal links. Do not sacrifice original value or factual correctness to chase rankings (which are not guaranteed).

## Efficient execution and issue handling
- Read this `AGENTS.md` at the start of Part 1. Look up exact source owners in `docs/CODEX_MAP.md` as needed. Read only relevant skills under `.agents/skills/`, not every file. Run one local Astro dev server; **native `src/` edits appear on localhost without Git staging**. Confirm the actual URL when testing.
- Reuse prior findings in ignored `.content/handoff.md` (`docs/CODEX_HANDOFF.md` gives a short format). Parts 1–4 use targeted checks; Part 5 runs the single full build/test/SEO/mobile audit. Avoid repetitive whole-repo scans, repeated research per language, duplicate builds, and unrelated refactoring.
- **Automatically fix genuine, reproducible technical/SEO/accessibility/mobile/localization defects**, including pre-existing issues, using the smallest safe change; retest and summarize fixes at the end of the stage. No permission needed for ordinary fixes. **Ask one grouped, specific question only if** a change conflicts with an approved owner rule, alters protected design/CTA/comparison/business behavior, requires missing material product facts, or risks destructive/irreversible work. Do not silently override rules or mislabel subjective tastes as bugs. Keep other unblocked work moving.
- End each stage with brief **implemented / checks and URL / genuine issues auto-fixed / approval-needed conflicts / blockers / next action**. Never claim a test was run if it wasn't. Update the handoff. No Git commit/push/deploy/indexing submission before the separately authorized Part 6.

## Setup and skills
Node >=22.19.0; `npm ci`; `npm run dev -- --host 127.0.0.1`; `npm run doctor`; `npm run check:quick`. Part 5 uses `npm run typecheck`, `npm test`, `npm run build`, `npm run validate` once, then relevant `npm run smoke:*` checks and optional visual comparison. Five scoped skills remain: `copywriting`, `copy-editing`, `site-architecture`, `web-design-guidelines`, `debug-optimize-lcp`.
